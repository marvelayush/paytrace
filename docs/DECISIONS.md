# Design decisions

A short log of choices and why. Newest at the bottom.

1. **Money as integer paise (BIGINT).** No floating-point rounding in matching. Converted to ₹ only for display. (A10)
2. **Surrogate keys where the spec lists none.** `upload_row_errors`, `claim_items` and `audit_log` get an `id`. `recon_results` uses `(run_id, order_id)` as its primary key because a run has exactly one result per order.
3. **Postgres enums as CHECK-constrained text, not native ENUM types.** Adding a status later is then a one-line migration with no `ALTER TYPE` problems.
4. **Auth with a JWT in an httpOnly cookie.** The token is never readable by JavaScript, which removes the XSS token-theft risk. `SameSite` and `Secure` come from env vars because the deployed frontend and backend run on different domains (decided at the deploy milestone).
5. **Role check as a FastAPI dependency (`require_role`).** A test sweeps the whole route table, so any new POST/PUT/PATCH/DELETE route that forgets the finance-only guard fails CI.
6. **bcrypt used directly** (not passlib, which is unmaintained and breaks with bcrypt 4.x).
7. **A separate `paytrace_test` database** is created by docker-compose so pytest never touches dev data.
8. **Columns added beyond the spec's data model:** `orders.awb`, because couriers' COD and freight files often carry only the AWB, so we need it to join; `recon_results.overpaid` (A12); `claims.updated_at` and `column_mappings.created_at` for the audit trail.
9. **The route sweep reads `API_ROUTERS`, not `app.routes`.** FastAPI 0.16x keeps included routers as lazy wrappers, so `app.routes` no longer lists their endpoints. Relying on that would have made the access test silently pass with zero routes. A second test cross-checks the sweep against the public OpenAPI schema.
10. **Login does not reveal whether an email exists.** Unknown emails get the same message and the same bcrypt work as a wrong password.
11. **The frontend checks the session in the browser (`AuthGate` calls `/auth/me`), not in a Next.js proxy.** The session cookie belongs to the API's domain, so the Next.js server can never see it in production. The API is the real security boundary; the frontend only decides what to render. Signed-in pages therefore export `instant = false` (Next 16 instant-navigation validation cannot prerender them).
12. **Navigation lists only screens that exist.** Items are added to `lib/nav.ts` as each screen ships, filtered by role, so there are never dead links or placeholder pages.
13. **No database foreign keys on the bulk tables** (orders, settlement/COD/freight lines, warehouse receipts, recon results). Postgres checks foreign keys row by row; with them, loading 1 lakh orders and 2.5 lakh lines took 31 s, without them 18 s. Only the ingest pipeline and the engine write these tables, and they take every partner/upload/run id from records they have just validated. Low-volume tables (users, partners, sources, mappings, uploads, rate cards, claims, audit) keep their foreign keys.
14. **Reconciliation keeps only the latest run's per-order results** (TRUNCATE + COPY inside the run's transaction, so readers never see a half-written run). Every run's timings and summary stay in `recon_runs`.
15. **The scalar engine (`expected.py`) is the specification, the Polars engine (`matching.py`) is the implementation.** A test runs both on 6,000 generated orders and requires identical expected amounts, taxes and freight.
16. **Benchmark measured end to end on real files**: the 100k-order month is written in every partner's layout and goes through the same `process_file` → `run_reconciliation` path as a real upload, so the number includes parsing, normalising, COPY in, matching and COPY out.
17. **Deployment: Neon + Render (blueprint) + Vercel.** Migrations run on every Render start (idempotent). JWT secret is generated by Render. API docs are off in production. Security headers are set on both apps. CORS takes a comma-separated origin list for preview deployments.
18. **Two ways for the browser to reach the API.** *Direct* (default, matches the spec's "uploads go straight to the backend"): `SameSite=None; Secure` cookie, blocked by Safari's third-party cookie rules. *Proxy*: set `BACKEND_URL` and `NEXT_PUBLIC_API_URL=/api` and Vercel forwards `/api/*`, making the cookie first-party (verified locally). A shared custom domain removes the trade-off. See deployment.md.
